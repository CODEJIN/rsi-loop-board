# 긴 평가 대응 설계 (딥러닝 모델 개선용)

작성 2026-10-25. 대상은 phase0/loop.py, Spec `evaluation`, 대시보드 반복 상세 화면이다.

## 1. 문제

딥러닝 모델 개선(경량화, 학습 설정 등)은 후보 하나를 평가하는 데 수십 분에서 수 시간이 걸린다. 지금 루프는 평가 한 번이 끝나야 판정한다. 그래서 다음 문제가 생긴다.
- 가망 없는 후보도 끝까지 평가하느라 시간을 다 쓴다.
- 평가가 도는 동안 진행 상황이 보이지 않는다.
- 같은 검증셋으로 수십 번 고르다 보면 잡음에 과적합된다.

## 2. 다른 사람들은 어떻게 하는가 (조사 요약)

| 방식 | 출처 | 핵심 |
|---|---|---|
| 고정 시간 예산 | Karpathy autoresearch (2026.3) | 실험마다 학습을 벽시계 5분으로 고정한다. 모델이 커도 작아도 같은 계산량이라 결과를 바로 비교할 수 있다. 시간당 약 12회, 하룻밤에 약 100회. 에이전트는 train.py 하나만 고치고, 평가 코드는 고정한다. |
| 평가 단계(cascade) | AlphaEvolve (DeepMind 2025) | 싸고 빠른 검사부터 차례로 돌린다. 앞 단계에서 떨어진 후보는 비싼 평가까지 가지 않는다. |
| 비동기 병렬 평가 | AlphaEvolve, AIRA₂ (Meta 2026) | 동기식 단일 GPU 실행이 탐색의 병목이다. 워커 풀로 평가를 병렬로 돌린다. |
| 숨긴 일관 평가 | AIRA₂ | 검증 점수로만 고르면 긴 탐색에서 성능이 오히려 떨어진다. 원인은 주로 평가 잡음이다. 선택용과 별도인 일관된 평가로 최종 확인한다. |
| 실험 기록 유지 | AlphaEvolve 프로그램 DB, File-as-Bus (2026) | 시도와 점수를 지속 상태로 남겨 다음 제안의 근거로 쓴다. |
| 학습 곡선 조기 종료 | 다단계 충실도 HPO (Successive Halving·Hyperband 계열) | 같은 지점에서 기존 최고보다 확실히 나쁜 학습은 중간에 끊는다. |

## 3. 이번에 넣는 것

### 3.1 평가 단계 (`evaluation.stages`)
```yaml
evaluation:
  command: python3 evals/m/eval.py
  stages:
    - {name: smoke, args: "--stage smoke", timeout_min: 5}                         # 실행·형태·NaN 확인
    - {name: proxy, args: "--stage proxy", timeout_min: 20, promote_within_pct: 3}  # 고정 예산 짧은 학습/부분 데이터
    - {name: full,  args: "--stage full",  timeout_min: 240}                        # 본 평가 — 판정은 마지막 단계 값으로
```
- 각 단계는 같은 평가 명령에 `args`를 붙여 실행한다. 계약(`--repo/--out/--label`, 결과 JSON)은 그대로다.
- 단계의 gate가 하나라도 실패하면 거기서 멈추고 후보를 기각한다.
- `promote_within_pct`를 쓴 단계에서는 후보 값이 같은 단계의 best 값보다 X% 넘게 나쁘면 다음 단계로 가지 않는다. 판정은 `rejected_early`(조기 탈락)이다.
- best를 잴 때는 모든 단계를 끝까지 돌려 단계별 기준값을 남긴다. 이 값은 지금처럼 커밋과 평가 설정 기준으로 캐시한다.
- 마지막 단계를 **홀드아웃**(선택에 쓰지 않은 데이터)으로 두면 AIRA₂의 일관 평가 역할을 한다. 설계 도우미가 이렇게 제안하게 한다.
- `stages`가 없으면 지금처럼 단계가 하나인 것으로 동작한다.

### 3.2 진행 보고와 조기 종료 (`evaluation.progress`, `early_stop`)
- `progress: true`이면 평가 명령에 `--progress <파일>`을 더 넘긴다. 평가 스크립트는 그 파일에 한 줄씩 `{"step": n, "total": N, "value": x}`를 붙여 쓴다. value는 val loss나 정확도 같은 감시 값이다.
- 루프는 이 파일을 읽어 `eval_progress` 이벤트로 보낸다(간격을 둠). 대시보드는 best 곡선과 함께 실시간으로 그린다.
- 단계별 `early_stop: {after_pct: 30, worse_pct: 10, patience: 2, direction: minimize}`를 지원한다.
  - 진행률이 after_pct를 넘은 뒤부터 확인한다.
  - 같은 step(가장 가까운 이전 지점)의 best 값보다 worse_pct만큼 나쁜 기록이 patience번 연속이면 평가를 중단한다. 판정은 조기 탈락이다.
  - total이 없으면 after_pct 대신 `after_step`을 쓴다.
- 원격 노드에서는 별도 SSH로 진행 파일 끝부분을 주기적으로 읽는다. 중단할 때는 `--label`의 고유 문자열로 원격 프로세스를 찾아 끝낸다.

### 3.3 기록
- 반복 기록(attempts)에 도달한 단계와 조기 탈락 사유를 남긴다. 그래서 planner와 구현자가 "proxy에서 떨어진 방향"을 피할 수 있다.

## 4. 이번에 넣지 않는 것 (후속)
- **비동기 병렬 평가:** 후보를 git worktree로 나눠 여러 GPU나 노드에서 동시에 평가하는 방식이다. GPU가 1장(RTX 4090)인 지금은 효과가 작다. 에이전트 작업과 평가를 겹치는 파이프라인은 다음 단계에서 다룬다.
- **원격 평가 분리 실행(detach):** SSH가 끊겨도 원격 평가가 계속되게 하는 것이다. 몇 시간짜리 평가에서는 필요하지만, Windows OpenSSH에서 세션이 끝난 뒤 자식 프로세스가 살아남는지 먼저 검증해야 한다. 지금은 SSH keepalive로 대응한다.
- **여러 목표(파레토):** 지금은 "정확도 하락은 gate, 지연은 objective"로 표현한다.

## 5. 평가 스크립트 작성 가이드 (설계 도우미에 반영)
- proxy 단계는 **고정 시간 예산**(예: 학습 10분)이나 **고정 데이터 부분집합**으로 만든다. 그래야 후보끼리 공정하게 비교된다.
- 시드, 데이터 순서, cudnn 결정성을 고정하고, 지연 측정은 워밍업 뒤 중앙값으로 잰다.
- 마지막 단계는 선택에 쓰지 않은 홀드아웃으로 확인한다.
- 정확도 하락 허용치는 gate로 둔다(예: top-1 −0.5%p 이내).
